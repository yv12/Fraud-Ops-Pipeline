# FraudOps Pipeline

An end-to-end automated fraud detection system that simulates how banks and payment companies keep their AI models accurate, auditable, and safely replaceable — without any manual engineering work.

**🚀 Deployed on Railway** — The entire pipeline runs in the cloud with auto-initialization, automatic model training, and a live WebSocket dashboard.

---

## What This Project Simulates

Every time you swipe your credit card, a machine learning model behind the scenes decides in milliseconds whether to approve or block the transaction. But here's the problem: **fraudsters are always changing their tricks**. A model that catches fraud today will slowly become blind to new patterns tomorrow.

This project simulates the **complete lifecycle** of that fraud-detection AI — not just training a model once, but keeping it alive, monitoring it, retraining it when the world changes, and replacing it only when a newer version mathematically proves it's better.

### The 5-Phase Pipeline

| Phase | Name | What It Does |
|-------|------|-------------|
| 1 | **The Foundation** | Sets up the database (DuckDB) that permanently records every transaction, every AI prediction, and every confirmed fraud report. This is the audit trail. |
| 2 | **The Baseline** | Trains a simple first AI model on historical data and registers it in MLflow as the "Production" model. A simulator sends mock transactions to test it. |
| 3 | **The Serving API** | A FastAPI web server that scores every incoming transaction in real time. When a new "Candidate" model exists, it secretly scores the same transaction in the background (shadow mode) without affecting real decisions. |
| 4 | **The Watchdog** | Uses Evidently AI to continuously check if fraud patterns have changed (data drift). If they have, it automatically retrains a new model and registers it as a Candidate. |
| 5 | **The Judge** | Compares the Candidate model against the Production model using real outcomes. If the new model has **both higher Precision and higher Recall**, it gets promoted. Otherwise, it's discarded. No unproven model ever touches live traffic. |

### Live Dashboard

The project includes a real-time web dashboard (available both locally and on Railway) with:
- **Live scoring view** — Watch transactions flow through both models in real time, with risk scores (1-99) and fraud/normal decisions
- **Architecture diagram** — An interactive, animated visualization of the entire data flow pipeline

## Where This Is Used in the Industry

This is not a theoretical exercise. Every major financial institution runs a version of this pipeline:

- **Visa, Mastercard, and payment networks** use real-time ML scoring on every single card transaction globally. Their systems process thousands of transactions per second and must catch fraud without blocking legitimate customers.
- **Banks (JPMorgan, HDFC, ICICI, SBI)** deploy fraud scoring models at the point of transaction authorization. They face the exact same drift problem — fraudsters adapt, and models must be retrained and validated continuously.
- **UPI and digital wallets (PhonePe, Google Pay, Paytm)** apply similar scoring to flag suspicious transfers in real time.
- **E-commerce platforms (Amazon, Flipkart)** use fraud models to detect fake accounts, payment fraud, and return abuse.

The core architecture — **serve → monitor → retrain → validate → promote** — is the industry standard pattern known as **MLOps** (Machine Learning Operations). Companies like Google, Netflix, and Uber have published papers describing nearly identical pipelines.

## How This Extends to Credit Risk & CIBIL Scoring

The exact same pipeline architecture can be adapted for **credit risk assessment** — the system that decides whether someone should get a loan, a credit card, or a mortgage.

### What Is Credit Risk / CIBIL?

When you apply for a loan, the bank checks your **credit score** (like CIBIL in India, FICO in the US, or Experian globally). This score is generated by a model that looks at your repayment history, existing debt, income patterns, and hundreds of other signals to predict: **"Will this person pay back the loan or default?"**

### Why This Pipeline Fits Perfectly

| Fraud Detection (Current Project) | Credit Risk / CIBIL (Extension) |
|---|---|
| Input: Card transaction (amount, time, location) | Input: Loan application (income, debt, history) |
| Output: Risk score → Approve or Block | Output: Credit score → Approve, Reject, or Adjust Interest Rate |
| Ground Truth: Chargeback arrives weeks later | Ground Truth: Default/repayment status arrives months later |
| Drift: Fraudsters change tactics | Drift: Economic conditions change (recession, inflation, new regulations) |
| Cost of failure: Lost money (missed fraud) or lost customer (false block) | Cost of failure: Bad loan (default) or lost business (rejected good applicant) |

### What Would Change

To convert this pipeline into a credit risk system, you would:

1. **Swap the data** — Instead of transaction features (V1-V28, Amount), use borrower features (income, employment years, existing EMIs, credit utilization, repayment history)
2. **Adjust the ground truth delay** — Fraud chargebacks arrive in weeks; loan defaults can take 3-12 months. The monitoring window would be longer.
3. **Change the threshold logic** — Instead of a binary fraud/not-fraud at 0.5, credit scoring uses risk bands (e.g., 300-900 CIBIL range) that map to different interest rates and loan amounts.
4. **Add regulatory compliance** — Credit decisions are heavily regulated (RBI guidelines in India, Fair Lending Act in the US). The audit trail from DuckDB becomes even more critical here.

**Everything else stays the same**: the shadow scoring, the drift monitoring, the automated retraining, the validation rules, and the model promotion logic. The pipeline is model-agnostic — it doesn't care whether the AI inside is detecting fraud or predicting loan defaults. It just makes sure whatever model is running stays accurate and accountable.

## Quick Start (Local)

```bash
# 1. Create virtual environment
python -m venv .venv
.venv\Scripts\activate        # Windows
source .venv/bin/activate     # Mac/Linux

# 2. Install dependencies
pip install -r requirements.txt

# 3. Set up database and train baseline model
python setup_db.py
python train_baseline.py

# 4. Start the API (auto-starts simulator in background)
uvicorn api:app --port 8000

# 5. Open the dashboard
# Visit http://localhost:8000/ in your browser
```

> **Note:** The dataset (`Data/creditcard.csv`) is not included in this repository due to its size. Download it from [Kaggle](https://www.kaggle.com/datasets/mlg-ulb/creditcardfraud) and place it in the `Data/` folder.

## Deploy to Railway (Cloud)

This project is configured for one-click deployment on [Railway](https://railway.app/).

1. **Push to GitHub** — Railway deploys directly from your repo.
2. **Create a new Railway project** and add a service from your GitHub repository.
3. **Set the port** to `8000` in Settings → Networking.
4. **Deploy** — On startup, the app will automatically:
   - Create the database schema
   - Train the baseline model (if no Production model exists)
   - Start the transaction simulator in the background
   - Serve the live dashboard

### Environment Variables (Optional)

| Variable | Purpose | Default |
|---|---|---|
| `DATABASE_URL` | PostgreSQL connection string (Railway provides this) | Falls back to local DuckDB |
| `MLFLOW_TRACKING_URI` | Remote MLflow server URL | Falls back to local `sqlite:///mlflow.db` |

> When `DATABASE_URL` is set, the app automatically switches from DuckDB to PostgreSQL — no code changes needed.
